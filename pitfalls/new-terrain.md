# New Terrain (`--new-terrain`) Pitfalls

## Dark / near-black patches on terrain even with the sun overhead (Fixed 2026-09-17)

### Problem
With `--new-terrain`, large amorphous areas of the ground rendered very dark /
near-black even at midday with the sun directly overhead. Characters, trees and
the sky looked correct; only the terrain was shadowy.

### Root cause
`--new-terrain` renders each block as a Bevy PBR `StandardMaterial` fed by a
baked `block_X_Y_normal.png` (the entity is `NotShadowCaster`, so it is **not**
its own shadow). The normal maps were generated by the external
`rose-zone-converter` tool with the height-gradient normal written in
**world-space order** instead of **tangent-space order**:

```rust
// WRONG (rose-zone-converter/src/main.rs, generate_normal_map)
let n = Vec3::new(-dx * 2.5, 1.0, -dy * 2.5).normalize(); // R=slope, G=up(1.0), B=slope
```

A tangent-space normal map must store the out-of-surface component in **blue**
(flat = `(0.5,0.5,1.0)`, blue ~= 255). Putting the `1.0` "up" term in green and a
slope term in blue made Bevy's TBN reconstruct shading normals lying almost in
the ground plane, and on ~half the texels the blue value fell below 128 (normal
tilted *into* the surface) -> `dot(N, sun) ~ 0` under an overhead sun -> black
patches. Measured on a still-broken block: mean G=189, 48.4% of texels B<128.

### Solution
Build the tangent-space normal as `(-dx, -dy, +1)` (u -> +world X, v -> +world Z,
so the bitangent/green term is `-dy`) and keep the up-term in blue:

```rust
// FIXED
let n = Vec3::new(-dx * 2.5, -dy * 2.5, 1.0).normalize();
```

Regenerated the normal maps with the converter. A corrected flat block now reads
`(127,127,254)` and 0.0% of texels are B<128.

### Files modified
- `rose-zone-converter/src/main.rs` - `generate_normal_map` channel order (bake tool)
- `src/render/shaders/terrain_material.wgsl` - NOT the cause: the legacy (non
  `--new-terrain`) `TerrainMaterial` is a separate custom Lambert shader. A
  half-lambert tweak here was tried and reverted because it does nothing for the
  `--new-terrain` PBR path.

### Lesson learned
- Bevy `StandardMaterial` normal maps are **tangent-space** (OpenGL, +Y up,
  out-of-surface in blue). Never bake a world-space normal `(slope, up, slope)`
  straight into RGB.
- A normal map **cannot** turn flat ground fully black under an overhead sun if
  the blue (out-of-surface) channel is correct; if it does, suspect a channel /
  handedness mismatch or wrong vertex normals, not lighting.
- Regenerated assets are read fresh at process start - fully restart the client
  to see a re-baked normal map, and remember `target/debug` and `target/release`
  hold separate copies of `3Ddata`.
