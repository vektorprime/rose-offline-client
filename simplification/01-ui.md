## Finding 1 — tooltips.rs: 14 near-identical skill-type match arms (biggest single win)

**Location:** `src/ui/tooltips.rs:1216-1602` (the `match skill_data.skill_type` inside `ui_add_skill_tooltip`)

**Problem:** Every one of the 14 `SkillType` arms repeats the same skeleton:

```
if !matches!(tooltip_type, SkillTooltipType::NextLevel) { add_skill_name(...); }
add_skill_type_and_target / add_skill_type ...
add_skill_use_ability_value(...)
[add_skill_power / add_skill_cast_range / add_skill_aoe_range / add_skill_status_effects ...]
add_skill_requirements(...)
add_skill_description(...)
if matches!(tooltip_type, SkillTooltipType::Extra) {
    if let Some(next) = add_skill_next_level(...) { ui_add_skill_tooltip(NextLevel...) }
}
```

Arms differ only in 1–3 of the middle `add_skill_*` calls. The `NextLevel` recursion block alone is duplicated 14× (~6 lines each).

**Suggestion:** Replace with a small data table: `match skill_type { ... }` returning a `&[fn(&mut egui::Ui, &GameData, Option<&PlayerTooltipQueryItem>, &SkillData)]` list of the differing middle functions, then one shared driver loop handles name/requirements/description/next-level. Or group arms by which middle set they use (there are only ~6 distinct combinations).

**Also in this file:**
- `ability_values_get_value(...)` with the same 14 positional `Some(player.xxx)` args is repeated 3× (lines 255-272, 780-797, 1155-1172). Add a method `PlayerTooltipQueryItem::get_ability_value(AbilityType) -> Option<i32>` in this file; saves ~40 lines and removes a fragile call signature.
- `add_equipment_item_name` (60-82) vs `add_stackable_item_name` (84-100) are identical except the source of the item name; merge into one helper.
- `ItemClass::EngineFuel / SkillBook / MagicItem / RepairTool` arms at 548-597 are 4 identical copies of the same code (plus a 5th `_` arm doing the same). Collapse into a single body.
- `add_skill_next_level` (674-715) re-implements the name-formatting from `add_skill_name` (652-672); extract a shared `skill_name_text(skill_data)` helper.

**Estimated savings:** ~300–350 of 1603 lines (≈20%).

## Finding 2 — ui_settings_system.rs: one 2140-line monolith of copy-paste grid rows

**Location:** `src/ui/ui_settings_system.rs:201-2116` (single `ui_settings_system` fn with a 17-arm `SettingsPage` match)

**Problem:** ~120 label+slider/checkbox grid rows, each written out as:

```rust
ui.label("X:");
ui.add(egui::Slider::new(&mut settings.field, min..=max).show_value(true));
ui.end_row();
```

(8 lines each, repeated ~120×). Also repeated: the "clamp min/max after grid" blocks (3×), the "Tip: ..." separator+label endings (12×), ComboBox-with-`selected_text`+`selectable_value` lists (8×), and the "GHOSTING DEBUG" panels.

**Suggestion:**
1. Helper fns: `settings_slider(ui, "label", &mut value, min..=max)`, `settings_checkbox(ui, "label", &mut bool)`, `settings_combo(...)` — each row drops from 8 lines to 1–2.
2. Extract each `SettingsPage::X` arm into its own `fn render_x_page(ui, settings...)` (17 small fns); the main system becomes a thin dispatcher. This also removes the need for the giant `SettingsSystemParams` SystemParam struct (175-199) since sub-fns can take `&mut` slices of the destructured params.
3. The `StarrySkyRender` and `PostProcessing` "debug" pages (840-970, 1686-1729) are dev-only; gate behind a `cfg(debug_assertions)` or a settings flag.

**Estimated savings:** ~400–500 of 2140 lines, plus large maintainability gain.

## Finding 3 — ui_minimap_system.rs: 3 copy-pasted icon-drawing blocks

**Location:** `src/ui/ui_minimap_system.rs:586-625` (players), `628-665` (NPCs), `668-723` (monsters)

**Problem:** All three blocks share the same ~30-line body with only the source iteration and tint differing:

```rust
let icon_scale = zoom.clamp(0.75, 1.5);
let icon_size = Vec2::new(icon_image.width, icon_image.height) * icon_scale;
let icon_rect = ...; if minimap_rect.contains_rect(icon_rect) { draw/hover }
```

The monster block re-implements sprite drawing manually via `Mesh::add_rect_with_uv` (700-707) instead of using `UiSprite::draw` like the others, and the player-arrow block (725-812) hand-builds a rotated quad mesh (~90 lines) that could be `ui.painter().add(Shape::mesh)` with a small rotate helper.

**Suggestion:** One helper `draw_minimap_icon(ui, ui_state, minimap_rect, zoom, pos, icon: &UiSprite, tint, hover_text)`; the three blocks become 10-15 lines each.

**Estimated savings:** ~110 of 966 lines.

## Finding 4 — ui_chatbox_system.rs: per-channel duplication + a literal copy-paste bug block

**Location:** `src/ui/ui_chatbox_system.rs:115-247` and `473-568`

**Problem:**
1. 9 event arms (Say/Shout/Whisper/Party/Clan/Allied/Announce×2/System/Quest) all do the same `textbox_layout_job.append(format!("{}> {}\n", name, text), 0.0, TextFormat { color: CHAT_COLOR_X, ..Default })`. Reduce to one `append_line(text, color)` fn; the match can return a `(String, Color32)` pair.
2. The entire `/ping` handling block (lines 497-511) is **copy-pasted verbatim** at lines 512-526 — the second copy is dead (unreachable, `else if` after the identical `if`). Delete it (15 lines).
3. The channel-button handlers (571-598) share the `clear + push prefix` pattern (3 of 5 do the same thing with a different prefix char).

**Suggestion:** `match event { ... -> (String, Color32) }` then one append call; delete the duplicate `/ping` block; collapse prefix buttons into a loop over `[(btn_response, '!'), ...]`.

**Estimated savings:** ~80 of 599 lines.

## Finding 5 — ui_number_input_dialog_system.rs: 10 digit-button copy-paste blocks + shared modal blocker

**Location:** `src/ui/ui_number_input_dialog_system.rs:206-254`

**Problem:** 10 nearly identical blocks (`if response_button_N.clicked() { current_value.push('N'); move_cursor_to_position(...); }`) — only the digit literal differs. The whole file also re-implements the modal full-screen interceptor that `ui_message_box_system.rs:112-128` already builds (identical ~16-line `Area::new("modal_*")` + rect_filled black overlay).

**Suggestion:** Iterate `for (digit, response) in [(b'0', &response_button_0), ...]` or store the digit buttons in a `[Option<Response>; 10]` array. Extract the modal blocker into a shared helper (e.g., `fn draw_modal_blocker(ctx, id)`) used by both message box and number input systems.

**Estimated savings:** ~70 of 295 lines.

## Finding 6 — widgets/*: 17 structs repeating the same position field boilerplate

**Location:** every widget file, e.g. `button.rs:13-61`, `editbox.rs:11-46`, `gauge.rs:11-39`, `listbox.rs:11-44`, `image.rs:14-43`, `scrollbar.rs:11-36`, `tab_button.rs:13-53`, `checkbox.rs:11-39`, `pane.rs:11-31`, `radio_button.rs:13-51`, `table.rs:11-41`, `zlistbox.rs:11-30`, `scrollbox.rs:14-50`, `draw.rs:9-27`, `draw_text.rs:10-29`, `caption.rs:11-24`, `radio_box.rs:11-16`, `skill.rs:11-30`

**Problem:** Every widget declares the same 8 serde fields verbatim (`ID`, `NAME`, `X`, `Y`, `OFFSETX`, `OFFSETY`, `WIDTH`, `HEIGHT`) plus `widget_to_rect!` (mod.rs:6-18), plus a `LoadWidget` impl that is empty for 5 widgets (listbox, editbox, caption, radio_box, table, zlistbox, draw_text, draw) and the same "load N sprites by name" for the rest.

**Suggestion:** A shared `WidgetCommon` struct with `#[serde(flatten)]` (or a `WidgetRect` mixin) holding id/name/x/y/offset_x/offset_y/width/height; each widget becomes `pub common: WidgetCommon` + its own fields. The `widget_to_rect!` macro can be replaced by one method on `WidgetCommon`. Also delete the empty `LoadWidget` impls (already default no-op pattern in `LoadWidget` trait) — either make the trait default or keep only the ones doing real work.

**Estimated savings:** ~250–300 lines across the widget files.

## Finding 7 — widgets/mod.rs: 5 giant same-shaped match arms on `Widget`

**Location:** `src/ui/widgets/mod.rs:131-226` (`id`, `draw_widget`, `load_widget`) and `264-361` (`get_widget`, `get_widget_mut` — each ~50 lines with a 16-variant `continue` list)

**Problem:** ~200 lines of pure dispatch boilerplate. Every new widget variant must be added to 5 match arms.

**Suggestion:** A `widget_match!` macro (one arm body expanded into all five), or an `enum_dispatch`-style approach; `get_widget`/`get_widget_mut` can also be collapsed to one fn via a generic recursion helper since only `Pane`/`TabbedPane`/`Skill` are containers.

**Estimated savings:** ~120 lines; mostly removes a maintenance footgun.

## Finding 8 — repeated "40×40 slot grid" rendering in 6 systems

**Locations:**
- `ui_inventory_system.rs:657-682` (6×5 grid)
- `ui_npc_store_system.rs:553-575` (6×8 store grid), `603-620` + `624-641` (2×5 buy/sell grids)
- `ui_bank_system.rs:227-247` (40 slots)
- `ui_personal_store_system.rs:288-313` + `315-341` (2× 6×5 grids)
- `ui_quest_list_system.rs:269-287` (6 fixed item slots)
- `ui_hotbar_system.rs:300-319` (8 slots)

**Problem:** The same idiom appears ~8 times: `for row { for col { slot(ui, pos(10 + col*41, 50 + row*41), ...) } }` inside an `allocate_ui_at_rect` 40×40 slot. Each system also re-declares `let mut dropped_item = None;` + `DragAndDropSlot::with_item/with_skill/new(...)` + `allocate_ui_at_rect` + `on_hover_ui(ui_add_item_tooltip)`.

**Suggestion:** A shared `ui_grid_slots(ui, origin, cols, rows, |ui, index| ...)` helper, plus a small `tooltip_on_hover(response, game_data, player_tooltip_data, item)` helper (currently duplicated at inventory_system:280-284, npc_store:184-189/287-293/369-375, bank:90-94, hotbar:139-164, personal_store:112-121, quest_list:64-68).

**Estimated savings:** ~100–150 lines + consistent behavior.

## Finding 9 — drag-drop accept predicate boilerplate

**Location:** `src/ui/ui_inventory_system.rs:146-191`

**Problem:** 8 micro-functions (`drag_accepts_equipment`, `drag_accepts_equipment_or_bank`, ...) that are just a page-type check + an optional "or Bank". Meanwhile `ui_bank_system.rs:74-78` and `ui_npc_store_system.rs:192-201` re-implement their own inline closures.

**Suggestion:** One helper `fn drag_accepts(page: InventoryPageType, allow_bank: bool, source: &DragAndDropId) -> bool`; the 8 fns collapse to 4 one-line callbacks or disappear entirely.

**Estimated savings:** ~30 lines (small, but removes a whole pattern).

## Finding 10 — window + dialog-acquisition boilerplate across ~13 systems

**Locations:** window boilerplate `egui::Window::new(...).frame(egui::Frame::none()).title_bar(false).resizable(false).default_width(dialog.width).default_height(dialog.height)` at: ui_inventory_system.rs:549-556, ui_npc_store_system.rs:498-506 + 582-590, ui_bank_system.rs:173-179, ui_chatbox_system.rs:270-277, ui_hotbar_system.rs:268-275, ui_skill_list_system.rs:160-166, ui_skill_tree_system.rs:214-220, ui_personal_store_system.rs:268-274, ui_login_system.rs:111-118, ui_server_select_system.rs:59-66, ui_character_select_system.rs:97-104, ui_game_menu_system.rs:58-66, ui_minimap_system.rs:409-425.

Dialog acquisition: `dialog_assets.get(&ui_resources.dialog_x) else { return }` (23 occurrences) vs. `DialogInstance::get_mut(...)` (ui_inventory, ui_hotbar, ui_quest_list, ui_character_select, ui_message_box) — two competing mechanisms for the same thing.

**Suggestion:** One helper (e.g., `fn open_dialog_window(ctx, title, dialog, open) -> Option<WindowResponse>` or a small macro) for the standard fixed non-resizable dialog window. Unify dialog lookup on `DialogInstance` (which already caches a clone) or a single `ui_resources.dialog(...)` accessor.

**Estimated savings:** ~80–120 lines.

## Finding 13 — message/NumberInput dialog event plumbing (ok-callback boilerplate)

**Locations:** `ui_inventory_system.rs:385-401` and `720-735`, `ui_npc_store_system.rs:154-169`, `ui_personal_store_system.rs:91-110`, `ui_message_box_system.rs:74-110`

**Problem:** Every "show a dialog with an OK callback that writes a message into a `Messages<X>` resource" repeats:

```rust
ok: Some(Box::new(move |commands, qty| {
    commands.queue(move |world: &mut World| {
        let mut events = world.resource_mut::<Messages<PlayerCommandEvent>>();
        let _ = events.write(...);
    });
})),
```

**Suggestion:** Since several call sites already hold a `MessageWriter<...>`, the event types could carry the payload directly and the *dialog* write the message, or a tiny helper `write_via_world::<T>(world, payload)`; also consider making the dialogs generic over one `MessageWriter` rather than `&mut Commands` closures.

**Estimated savings:** ~40–50 lines.

## Finding 14 — data_bindings.rs linear scans (acceptable, but worth noting)

**Location:** `src/ui/widgets/data_bindings.rs` (146 lines)

**Problem:** Every widget draw does linear `iter().find()` scans over each of the ~12 binding arrays (per widget, per frame). With small arrays this is fine, but the *architecture* (12 parallel arrays of (id, payload) with bespoke getters) requires a getter per binding kind — 12 getters that all look identical. This is the "generic machinery" that is already mostly reasonable for the legacy-XML constraint.

**Suggestion:** Do not rewrite the binding model; only note that the `get_*` set could be generated by a macro (one `get` + one `set` with a typed payload). Low priority — biggest value is in the items above.

Also recommended (moderate effort, high maintainability): Findings 5-7 (digit loop + modal blocker share, widget field boilerplate, Widget match macro), Finding 10 (window boilerplate), Finding 8 (slot grid helper).
